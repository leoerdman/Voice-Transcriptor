## 1. Коротко

1. **Сломанного почти нет.** 365 из 365 вставок прошли, бэкенд сам не падал,
   ремонт языка (multi → ru) отработал во всех 40 спорных местах. Проблемы
   17–20.11 (шторм `press outcome=click`, 32 с ожидания на пустой записи,
   потерянный спул восстановления, истёкший сертификат GigaAM) в свежих логах
   больше не встречаются.
2. **Главная потеря времени — сохранение аудио на пути к вставке.** Deepgram
   отдаёт финал за 280 мс (медиана), а вставка начинается через ~2 с: окно
   сначала грузит WAV в бэкенд и ждёт ответа. Вынести сохранение из
   критического пути — это примерно −1 с на каждой диктовке.
3. **Второе — пересылки между процессами.** Хоткей идёт через
   `globalShortcut` → `executeJavaScript` в окно → ожидание подтверждения;
   вставка — два внешних процесса (JXA и osascript). У Hex всё это нативно в
   одном процессе. Переписывать приложение не нужно: быстрый путь (хоткей,
   вставка, буфер обмена, капсула) переезжает в постоянный нативный помощник.
4. **Цель (оценка):** отпустил → текст в поле ~0,6–0,8 с вместо ~2 с;
   нажал → запись идёт ~50 мс с тёплым микрофоном; капсула — мгновенно.

## 3. Где теряется время (по весу)

### 3.1 Сохранение WAV стоит до вставки — ~0,9–1,5 с на каждой диктовке

- `frontend/src/main.tsx` ~12680: двухпопыточный `saveRecordingText({...audio})`
  (`/api/recordings/save-with-audio`) выполняется **до** сигнала FINAL
  в main-процесс. Вставка ждёт, пока загрузится и запишется файл.
- По 173 записям: `finalize` 280 мс против `stopLive:done` 1213 мс —
  разница ~0,9 с стабильно.
- Отдельный вопрос: почему загрузка ~1 МБ по loopback занимает ~1 с. В примере
  ответ пришёл через 90 мс после того, как подключились тёплые сокеты
  (`rewarm` в `backend/main.py:6881`). `rewarm()` сам не ждёт
  (`backend/deepgram_warm.py:394`), но возможно, что event loop блокируется
  синхронной частью TLS-подключения или очисткой архива
  (`audio retention: removed …` в ту же секунду). Проверить профилированием.

### 3.2 Вставка — два внешних процесса на каждую вставку, ~400 мс

- `desktop/main.js:5351` `awaitModifierRelease` — запускает JXA (~240 мс на
  запуск процесса), опрашивает отпускание модификаторов, пол 150 мс,
  дедлайн 500 мс.
- `desktop/main.js:~5890` — `osascript -e` с «Edit › Paste» (~157 мс).
- `desktop/paste-capability.js:814` — пауза `attemptDelaysMs[0]=45` мс перед
  первой попыткой; два вызова `lsappinfo`.
- **Проверка почти выключена:** `desktop/paste-verification-policy.js:41`
  (`UNVERIFIED_STREAK_LIMIT = 2`): две подряд «нечитаемые» вставки (Claude
  desktop не отдаёт `AXValue`, ошибка -1728) — и проверка отключается до
  перезапуска. Итог: verified 14 из 308.
- **Побочный баг:** буфер обмена восстанавливается только при
  `verified===true` (`desktop/main.js:~5210`), поэтому в ~95% случаев текст
  диктовки остаётся в буфере вместо того, что там было.

### 3.3 Хоткей ходит через окно

- `desktop/main.js:2383,9654` — Electron `globalShortcut`.
- `desktop/main.js:2975` `toggleRecordingFromShortcut` →
  `await ensureBackgroundWindow()` → `desktop/renderer-toggle.js:34-70`
  (`executeJavaScript`, бюджет 2000 мс) → `waitForRendererRecordingStart`
  (до 8000 мс).
- В логах: однажды `toggle_hotkey failed reason=renderer-probe-timeout` —
  запись не началась. 7 раз `blocked reason=single-capsule-post-stop-active`:
  нажатие во время вставки предыдущей записи молча игнорируется.
- Момент нажатия не фиксируется у источника: всё, что успели сказать, пока
  окно отвечает, ловит только предзапись тёплого микрофона.

### 3.4 Последовательные ожидания до открытия микрофона

`frontend/src/main.tsx:11286-11455` (`startLive`), строго по очереди:
`ensureRecordingsArchiveReady` → гонка `readStaleLiveDraftOnce` с таймером
`staleReadWaitMs = 1500` (`:1086`, `:11332`) → `await createPcmSink` (OPFS,
50–500 мс) → `new WebSocket` → только потом микрофон. С тёплым микрофоном это
частично скрыто, с холодным добавляется ~310 мс (`frontend/src/capture-warm.ts:6`).

**Статус (2026-11-24, TASKS_2026-11-23 P2-4):** микрофон открывается сразу при
нажатии. Сессия (архив, сокет, sink, черновик), список устройств и граф
(`AudioContext` + worklet) идут рядом с ним — `frontend/src/live-start.ts`.

### 3.5 Тёплый микрофон не работает с Bluetooth — 13% записей

- `frontend/src/capture-warm.ts:140` — для Bluetooth `hold:false`. Это
  правильно: открытый BT-микрофон переводит наушники в режим гарнитуры (HFP),
  и звук у них портится.
- В логах: 22 из 173 записей — `warm hold=0 reason=bluetooth`
  (наушники Liberty 5). У этих записей каждый старт холодный.

### 3.6 Капсула пересоздаётся после 8 с простоя

- `desktop/main.js:515` `RECORDING_STATUS_CAPSULE_TEARDOWN_MS = 8000`,
  создание окна 110–380 мс.
- Причина осознанная: скрытое окно с `backgroundThrottling:false` держало
  компоновщик и ело ~13% ядра в простое (комментарий там же). Поэтому решение —
  не «держать BrowserWindow», а держать окно, которое не стоит CPU в простое
  (см. 5.4).
- Для обычной (не экранной) записи нет метрики «нажатие → капсула видна».

### 3.7 Прочее

- `stopTailHoldMs = 200` (`frontend/src/main.tsx:1282`) — фиксированная пауза
  на каждом стопе.
- `ScriptProcessorNode` всё ещё создаётся как запасной путь
  (`frontend/src/main.tsx:1191`) — 175–232 предупреждения в логах.
- Два сокета Deepgram (multi + ru) на каждую запись — двойная стоимость; второй
  поток отброшен (`adopted=False`) в 49 из 175 записей (28%). Причина не
  выяснена.

## 5. План работ

Каждый пункт — отдельный атомарный коммит с тестами (правила `AGENTS.md`).

### Волна 1 — быстрые правки без новой архитектуры (1–2 дня)

**1.1 Сохранение аудио — после вставки, а не до.** *(−0,9…1,5 с, главный пункт)*
- В `stopLive` отдать FINAL в main сразу по получении envelope; сохранение
  WAV и метаданных запускать параллельно.
- Сохранить гарантии: спул OPFS удаляется только после успешного сохранения
  (`deferredSinkDestroy`); ошибка сохранения видна пользователю (FL-02);
  двухпопыточное сохранение в запасную папку остаётся.
- Выяснить, почему загрузка ~1 МБ по loopback занимает ~1 с (event loop,
  `rewarm`, очистка архива), и убрать блокировку.
- Тест: стоп с медленным сохранением не задерживает сигнал FINAL.

**1.2 Envelope сразу после merge.** *(−0,2…0,5 с)*
Текст готов на +0,48 с, `session complete` — на +0,96 с (CloseStream второго
сокета пришёл через 235 мс). Отправлять envelope в окно сразу после
merge/recovery, а сокеты закрывать после.

**1.3 Параллельный старт.** *(−0,05…0,5 с на холодном старте)*
`ensureRecordingsArchiveReady`, чтение старого черновика и `createPcmSink`
запускать одновременно с открытием микрофона и WebSocket. Кадры до готовности
приёмника копить в памяти (как уже копятся `wsPendingFrames`).

**1.4 Хвост по голосу.** *(−0…0,2 с)*
Вместо фиксированных 200 мс: минимум 100–200 мс, дальше ждать, пока по уровню
сигнала идёт речь, до 600 мс; звук стоп-сигнала исключать.

**1.5 Восстановление буфера обмена без «verified».**
Восстанавливать по номеру изменения буфера (`changeCount`): если после нашей
записи буфер никто не трогал — вернуть прежнее содержимое через ~500 мс.
Пересмотреть `UNVERIFIED_STREAK_LIMIT`: считать «нечитаемость» по приложению,
а не на весь процесс.

**1.6 Хоткей во время вставки** — не игнорировать, а начинать новую запись
(капсула очереди) или хотя бы показывать причину.

### Волна 2 — нативный помощник для быстрого пути (3–5 дней, macOS)

Расширить `desktop/native/screen-input/` до постоянного процесса на всё время
работы приложения (сейчас он живёт только в экранном режиме). Протокол тот же:
JSON построчно через stdin/stdout.

**2.1 Вставка:** снимок буфера при старте записи, проверка фокуса и
`changeCount`, ⌘V через `CGEventPost` с маркером своего события, пауза
100 мс, восстановление буфера. Отпускание модификаторов проверять там же
(`CGEventSourceFlagsState`), без JXA. Запасной путь для «трудных» приложений —
печать Unicode-пачками. AppleScript остаётся аварийным путём.
*(вставка ~400 мс → ~120 мс)*

**2.2 Хоткей:** CGEventTap в отдельном потоке, App Nap выключен, тап
переключается заново при отключении, момент нажатия — `mach_absolute_time`
прямо в колбэке. Событие идёт сразу в main, а запись начинается задним числом
с этого момента из буфера предзаписи. `globalShortcut` остаётся запасным, если
нет разрешения Accessibility.

**2.3 Капсула как нативная панель** (NSPanel, nonactivating, alpha 0 в
простое, перерисовка только во время анимации). Создаётся один раз и не стоит
CPU. Если оставлять BrowserWindow — держать его скрытым с включённым
`backgroundThrottling`, а не уничтожать.

**2.4 Метрика `press_to_capsule_visible_ms`** для голосовой записи — по аналогии
с экранным режимом.

### Волна 3 — звук и Bluetooth

**3.1 AudioWorklet без запасного `ScriptProcessorNode`** (или запасной путь
только по факту отказа worklet). Убирает работу в основном потоке окна и
175+ предупреждений.

**3.2 Bluetooth:** настройка «при BT-наушниках писать со встроенного
микрофона» — тогда тёплый микрофон работает и наушники не переключаются в
режим гарнитуры. Сейчас это 13% записей с холодным стартом.

**3.3 Захват звука в нативном помощнике** (AVAudioEngine с кольцевым буфером) —
только если после 1.3 и 3.1 холодный старт всё ещё заметен. Это крупная
переделка: спул, предзапись и WebSocket сейчас живут в окне.

### Волна 4 — точность распознавания

**4.1 Почему второй поток отбрасывается в 28% записей** (`adopted=False`,
`backend/deepgram_dual.py`). Если причина — поздний коннект, то это двойная
стоимость впустую.

**4.2 Словарь, который собирается сам.** Keyterms Nova-3 сейчас заполняются
вручную (`backend/deepgram_keyterms.py`, лимит ~500 токенов). Пополнять из
истории: имена проектов и продуктов, слова, на которых multi ошибается.
Пример из диктовки 22.11: «транскиптер», и начало «Okay. That's not shift.»
(русская фраза, прочитанная как английская).

**4.3 Словарь из того, что на экране.** Текст фронтового окна (Accessibility
или Vision OCR на самом Маке) — в keyterms для REST-ремонта и для Upscale.

**4.4 Арбитраж языковой моделью.** В спорных местах dual-merge отдавать модели
оба варианта (multi и ru) и выбирать по смыслу, а не по уверенности. Опция,
+~1 с.

**4.5 Эталонный корпус.** 20–30 своих записей с исправленным текстом и
автоматический подсчёт ошибок (WER) на каждое изменение распознавания.

**4.6 Офлайн-запасной путь со стримингом** (Parakeet v3 / GigaAM v3 через GGUF,
как у Hex) — когда Deepgram недоступен. Сейчас при отказе Deepgram — пакетный
local без живого текста.

### Волна 5 — экранный режим

**5.1 Подписи «что обведено».** Через Accessibility узнать элемент под
штрихом (кнопка, поле, пункт меню, ссылка), запасной вариант — Vision OCR
внутри рамки. Вместо `[✏️1 красный, в центре]` —
`[✏️1 меню «Choose environment» в Claude]`. Агенту не нужно открывать
картинки: точнее и дешевле по токенам. Сейчас OCR и AX в экранном режиме нет.

**5.2 Контекст окна в шапке:** приложение, заголовок, URL вкладки, путь файла
в редакторе.

**5.3 Привязка штриха к слову по времени Deepgram,** а не по смещению в тексте
(`frontend/src/screen-annotations.ts:577`).

**5.4 Новые инструменты:** стрелка, маркер-выделение, «прожектор» (затемнить
всё, кроме области), текстовая подпись. Сейчас есть `rect` и `pen`
(`desktop/screen-mode.js:45-46`).

**5.5 Жесты без цели.** Штрихи, нарисованные «для выразительности» (как все
три 22.11), не должны превращаться в вырезки: отдельный жест или пометка
«жест».

**5.6 Режим «сразу задачи»:** языковая модель превращает сессию в нумерованный
список задач со ссылками «скрин 1, штрих 2».

### Волна 6 — наблюдаемость и шум

- Тексты Deepgram (`interim #N`, `is_final … text=`) — в отладочный буфер в
  памяти, не в `main.log`. Это ~24% журнала и приватный текст.
- `perm-check` — один раз за запуск и при изменении, а не на каждой записи.
- `upstream closed code=1011` на простаивающем тёплом сокете — INFO, не ошибка.
- Проверить дубли строк `backend-stderr` (склеенные и повторённые).
- Экран «Состояние за неделю»: p50/p90 этапов, ремонты, дыры, перепутанные языки.

### Windows и Linux (когда дойдёт)

Брать готовые решения Hex: `SendInput` с кодами из раскладки и ожиданием
модификаторов вместо VBS/PowerShell (cscript у нас до 3,5 с из-за Defender);
низкоуровневые хуки с переустановкой; на Linux XTest / wtype / портал
RemoteDesktop с удержанием сессии. Удобно делать помощник сразу на Rust, если
появится реальная потребность в трёх платформах.

## 7. Чего не делать

- **Не переписывать приложение на Rust/Swift целиком.** Узкое место — не язык,
  а пересылки между процессами и последовательные ожидания. Нативным должен
  стать только быстрый путь.
- **Не держать Bluetooth-микрофон открытым.** Это ломает звук в наушниках.
- **Не возвращать капсулу как вечно живой BrowserWindow с
  `backgroundThrottling:false`** — уже было, ~13% ядра в простое.
- **Не отключать dual-stream ради скорости**, пока не выяснена причина 28%
  отказов: он не добавляет задержки, только стоимость, а точность на русском
  держится на нём.

## 8. Как мерить

1. **Фикстура вместо микрофона** (как `HEX_AUDIO_FIXTURE`): режим, в котором
   захват читает WAV в реальном времени. Нужен для повторяемых прогонов.
2. **Две фазы на каждой сборке:** `start` (нажатие → первый кадр отправлен) и
   `finish` (отпускание → вставка завершена). Брать из уже существующих
   `trace-start`/`trace-end`, добавив `press_to_capsule_visible_ms`.
3. **Сравнение base/head чередующимися прогонами**, p50/p90 по 20+ прогонам.
4. **Срез по реальным логам раз в неделю:** те же метрики, что в разделе 2.
